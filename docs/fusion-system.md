# Fusion System — AI-forged tower combos

How a tower plus 2–3 powers becomes a unique, balanced, shareable effect generated by Ollama.
In short: **the LLM designs, the engine enforces rules and numbers, the database remembers.**

---

## 1. How big is the combo space?

The "640,000" figure is 10 towers × 40³, which counts **order** (A+B+C ≠ C+B+A). The
recommendation below is to ignore order:

| Interpretation | Per tower | × 10 towers |
| --- | --- | --- |
| Ordered, repeats allowed (40³) | 64,000 | 640,000 |
| **Unordered, repeats allowed, 2–3 powers** ← recommended | 820 pairs + 11,480 triples = **12,300** | **123,000** |
| Unordered, no repeats, 2–3 powers | 780 + 9,880 = 10,660 | 106,600 |
| Single power (hand-made, never generated) | 40 | 400 |

**Why unordered with repeats:**
- Players expect A+B+C to equal C+B+A. If order changed the result, it would feel random.
- There are about 5× fewer combos, so the shared database fills up about 5× faster. More cache
  hits means less waiting for everyone.
- Repeats (Ember + Ember + Ember) give **"pure" fusions**, which are great ascension moments.
- It's still a huge space. At about 15 s per generation, generating everything would take one
  GPU about **3 weeks**. So "generate all of it" stays possible, but we don't have to.

**Canonical key:** `v1:<tower>:<sorted power ids joined by +>`, e.g. `v1:arc:echo+frost+storm`.

**Pre-generate all pairs before launch** (8,200 of them, about 1–2 days on one GPU). Players
hit pairs early in every run, and nobody should wait on wave 4. That leaves **triples** as the
live discoveries, which are the exciting ones. For pairs, the first player to socket one gets
"First Wielder" credit instead of "Discoverer".

## 2. How can the LLM make unique effects without writing code?

| Approach | Unique? | Safe to share? | Small-model reliability | Balanceable? |
| --- | --- | --- | --- | --- |
| LLM writes JavaScript | Very | **No.** Arbitrary code would run on every player's machine | Poor. Small models write buggy code | No |
| LLM fills in parameters for fixed templates | No. Everything feels like a reskin | Yes | Great | Yes |
| **LLM puts together an effect graph from a small effect language (DSL)** | **Yes.** The variety comes from combining pieces | **Yes.** It's data, not code | **Good**, with schema-constrained decoding | **Yes**, through simulation |

The effect language is essentially **"Magic: The Gathering rules text as JSON."** We write about
70 small building blocks once (a trigger, a condition, an action, a movement pattern, and so
on). Each block is 20–80 lines of engine code. The LLM only picks blocks, sets their
parameters and wires them together. It can also **invent new nouns** (custom statuses,
projectiles and zones built from the same blocks), and that is where most of the uniqueness
comes from.

### Division of labor

| The LLM decides | The engine and server decide |
| --- | --- |
| Concept, name, flavor text | Every final number (the **potency** multiplier is solved by simulation, §8) |
| What happens, and when (the structure of rules) | Hard limits (entity caps, recursion depth, CC tenacity) |
| Custom statuses, projectiles, zones | Rules tooltip text (generated from the spec, never from LLM prose) |
| Palette, shapes, trail, impact, sound preset | Whether the result is new enough and fusion-like enough to keep |

## 3. Anatomy of a fusion spec

The field order matters. With constrained decoding the model writes fields in schema order,
so putting the **creative fields first** makes it "think" before it wires anything:

1. `concept`: 1–2 sentences on what makes this fusion special
2. `name` (≤ 32 chars), `flavor` (≤ 140 chars)
3. `attack`: optional changes to the chassis's base attack (projectile, count, pattern, burst)
4. `vars`: up to 3 per-tower counters (`{ id, max, reset: never | wave_start | on_idle }`)
5. `statuses[]`: up to 2 **custom statuses**
6. `projectiles[]`: up to 2 **custom projectiles**
7. `zones[]`: up to 2 **custom zones**
8. `rules[]`: 1–6 rules, each `{ when, if?, do[] }`
9. `visual`, `sound`

**The schema is flat and never recursive.** Grammar-constrained decoding struggles with deep
recursion, and so do small models. Nesting depth is fixed: *rule → actions* and *template →
actions*. Actions never contain other actions. For sequencing, every action can carry an
optional `delay` (seconds) and `repeat: { times, every }`. Templates refer to each other by
`id`.

## 4. The effect language, v1 (draft)

Units: distance in **tiles**, time in **seconds**. Every block is registered once in the
**primitive registry** (§4.7). The JSON Schema, the LLM cheat sheet, the validator and the
tooltip writer are all generated from that registry.

### 4.1 Triggers (`when`) — 18
`on_attack` · `on_hit` · `on_kill` · `on_crit` · `every_nth_attack{n}` · `every{seconds}` ·
`on_beat{n}` (global rhythm clock) · `on_idle{seconds}` · `on_enemy_enters_range` ·
`on_enemy_leaves_range` · `on_status_applied{status}` · `on_status_expired{status}` ·
`on_enemy_dies_in_range` · `on_projectile_end{projectile}` · `on_var_reached{var, value}` ·
`on_wave_start` · `on_wave_end` · `on_ally_hit` (a tower in this one's aura hit something;
this is how the Beacon conduit works)

### 4.2 Conditions (`if`, all must pass) — 12
`chance{p}` · `cooldown{seconds}` (internal cooldown) · `target_hp_below{pct}` ·
`target_hp_above{pct}` · `target_has_status{status, min_stacks}` · `target_lacks_status{status}` ·
`target_is{boss|flying|armored|shielded|fast|stealth}` · `var_at_least{var, value}` ·
`enemies_in_range_at_least{n}` · `target_distance{min, max}` · `first_hit_on_target` ·
`every_nth{n}` (a counter local to the rule)

### 4.3 Selectors (`to`, `around`) — 13
`target` (inside a status: the enemy carrying it) · `self` (the tower) · `impact` (a point) ·
`all_in_radius{radius, around}` · `random_in_range{n}` · `strongest_in_range{n}` ·
`weakest_in_range{n}` · `nearest{n, around}` · `chain{n, range}` (hops from the target) ·
`with_status{status, within}` · `path_ahead{distance}` (a point on the path ahead of the target) ·
`path_behind{distance}` · `towers_in_radius{radius}`

### 4.4 Actions (`do`) — 26
| Group | Actions |
| --- | --- |
| Damage | `damage{to, amount, type}` · `explode{at, radius, amount, type}` · `execute{to, below_pct}` |
| Status | `apply_status{to, status, stacks, duration?}` · `remove_status` · `consume_status{status}` (puts the consumed stack count into `{consumed}` for the actions after it) · `spread_statuses{from, radius}` · `mark{to, amp, duration}` |
| Movement | `knockback{to, distance}` · `pull{to, toward, strength}` · `teleport_along_path{to, distance}` (negative = backward) · `rewind_position{to, seconds}` · `swap_positions{a, b}` · `shrink{to, hp_mult, speed_mult}` |
| Spawns | `fire_projectile{projectile, from, toward, count, spread}` · `create_zone{zone, at}` · `summon_drone{count, lifetime, sting}` |
| Tower | `repeat_attack{delay, mult}` · `modify_tower{to, stat, mult, duration}` · `set_var` · `add_var` |
| Meta | `grant_gold{amount}` (capped) · `restore_life` (capped) · `reveal{to}` · `break_shield{to}` · `retarget{mode}` |

Every action can also take `delay` and `repeat: { times, every }`.

### 4.5 Templates the LLM can invent
- **Status:** `{ id, name, stacking: refresh|add|independent, max_stacks, duration, speed_mult,
  damage_taken_mult, armor_delta, stores_damage (0–1), tick{every, do[]}, on_apply[],
  on_expire[], on_death[], visual{tint, icon} }`
- **Projectile:** `{ id, motion, speed, size, lifetime, pierce, bounce, amount, type, on_hit[],
  on_end[], visual{shape, trail} }`. Motions: `straight · homing · lob · boomerang · orbit ·
  spiral · sine · sky_drop · path_crawl (walks the path backwards) · hitscan · mine`
- **Zone:** `{ id, shape: circle|ring|cone|path_segment, radius|length, duration,
  follows: none|target|tower, speed_mult, tick{every, do[]}, on_enter[], on_exit[], visual }`
- **Visual:** `{ palette[3 hex], projectile: orb|shard|star|ring|crescent|needle|glyph|bubble|spark,
  trail: none|line|sparkle|smoke|ribbon|afterimage, impact: burst|ring|shatter|splash|implode|glyph,
  aura: none|halo|orbit_motes|flicker|embers }`
- **Sound:** `{ preset: zap|pew|boom|chime|thud|hiss|warble|pluck, pitch: 0.5–2 }`

### 4.6 Values
A value is a number or a small expression (max depth 3):
- `{ "dmg": 0.6 }`: 60% of the tower's **current** damage. This scales with tier and potency.
  **All damage should be written this way.**
- `{ "var": "toll" }` · `{ "stacks": "chill" }` · `{ "consumed": true }` · `{ "stored": "stasis" }`
- `{ "target_hp_pct": true }` · `{ "enemies_in_range": true }` · `{ "distance_traveled": true }`
- `{ "add": [a, b] }` · `{ "mul": [a, b] }` · `{ "min": [a, b] }` · `{ "max": [a, b] }` ·
  `{ "clamp": [x, lo, hi] }`

### 4.7 The primitive registry (one file per block, the only source of truth)

```ts
export const knockback = defineAction({
  name: 'knockback',
  doc: 'Push enemies backward along the path by `distance` tiles.',   // → LLM cheat sheet
  params: z.object({ to: Selector, distance: Value }),                  // → JSON Schema + validation
  limits: { distance: [0.1, 3] },                                       // → clamped at runtime too
  describe: (p) => `knock ${sel(p.to)} back ${val(p.distance)} tiles`, // → tooltip text
  tags: ['movement', 'control'],                                        // → novelty + lint
  run(ctx, p) {
    for (const e of ctx.select(p.to)) ctx.moveAlongPath(e, -ctx.eval(p.distance));
  },
});
```

**Adding a new block is one file, and the LLM can use it on the next generation.** The
prompt, schema and engine can't drift apart.

## 5. Worked example

**Arc + Frost + Echo → "Glacial Carillon"** (as it might come out of Stage B):

```json
{
  "dsl": 1,
  "concept": "Frozen enemies become bells. Striking one makes every other frozen enemy in range ring with an echo of the hit, and the peal grows louder with every bell made this wave.",
  "name": "Glacial Carillon",
  "flavor": "Every frozen heart is a bell waiting to be struck.",
  "vars": [{ "id": "toll", "max": 12, "reset": "wave_start" }],
  "statuses": [{
    "id": "bellfrost", "name": "Bellfrost", "stacking": "refresh",
    "duration": 2.5, "speed_mult": 0.35,
    "on_expire": [
      { "action": "damage", "to": "target", "type": "frost",
        "amount": { "mul": [{ "dmg": 0.15 }, { "var": "toll" }] } }
    ],
    "visual": { "tint": "#bfefff", "icon": "bell" }
  }],
  "rules": [
    { "when": { "event": "on_hit" },
      "do": [{ "action": "apply_status", "to": "target", "status": "chill", "stacks": 1 }] },
    { "when": { "event": "on_status_applied", "status": "freeze" },
      "do": [
        { "action": "apply_status", "to": "target", "status": "bellfrost" },
        { "action": "add_var", "var": "toll", "amount": 1 }
      ] },
    { "when": { "event": "on_hit" },
      "if": [
        { "check": "target_has_status", "status": "bellfrost" },
        { "check": "cooldown", "seconds": 0.5 }
      ],
      "do": [
        { "action": "damage", "type": "frost", "delay": 0.25,
          "to": { "select": "with_status", "status": "bellfrost", "within": "range" },
          "amount": { "dmg": 0.5 } }
      ] }
  ],
  "visual": { "palette": ["#9be7ff", "#e8fbff", "#4a6cf7"], "projectile": "shard",
              "trail": "sparkle", "impact": "ring", "aura": "orbit_motes" },
  "sound": { "preset": "chime", "pitch": 1.25 }
}
```

**Tooltip generated from the spec** (after the balance pass set potency P = 1.2, so damage ×1.2 and CC durations ×√1.2):
> **Glacial Carillon** · Arc · Frost · Echo
> - On hit: apply 1 Chill.
> - When an enemy becomes Frozen: apply **Bellfrost** (−65% speed, 2.7 s) and gain 1 Toll (max 12, resets each wave).
> - On hit against a Bellfrosted enemy (0.5 s cooldown): 0.25 s later, **every** Bellfrosted enemy in range takes 60% damage as Frost.
> - When Bellfrost wears off: the enemy takes 18% damage × Toll as Frost.

**The chassis changes the result.** Here's the same trio, Ember + Gravity + Echo, on three
towers (made-up examples of the target quality):
- **Cannon → "Collapsing Sun":** shells leave a small sun that pulls enemies in. It detonates
  twice, and the burn grows with how many enemies it caught.
- **Rail → "Event Horizon Lance":** the shot leaves a burning line. 0.4 s later the line
  collapses, pulling everything onto its center line and hitting again.
- **Beacon → "Hearthwell":** when a tower in the aura hits an enemy, it gets dragged slightly
  toward the Beacon. Burning enemies inside the aura catch fire again when their burn ends.

## 6. Generation pipeline

```
forge(tower, powers)
  │
  ├─► DB lookup by canonical key ───────────────► hit → return (≈ 10 ms)
  │
  ├─► already generating the same key? ─────────► attach to that job (no duplicate work)
  │
  └─► priority queue  (player waiting  >  pre-generation)
        │
        1. Build context
        │    chassis card · 2–3 power cards (tags, text, base spec) · twist seed (§7)
        │    3–5 rotating example fusions · "avoid" list (concepts of the ~10 closest
        │    existing fusions)
        │
        2. Stage A: Concept           temp ≈ 0.9   format: {name, concept, flavor, mechanics[3–5]}
        │    Plain-English design. Creative, loosely constrained.
        │
        3. Stage B: Compile           temp ≈ 0.3   format: full JSON Schema of the effect language
        │    Turns the sketch into a spec. The cheat sheet (~2k tokens) plus examples are in context.
        │
        4. Validate:  schema → references resolve → limits → fusion lint → novelty
        │    └─ fail → repair prompt listing the exact errors (up to 2 rounds)
        │
        5. Balance:   headless sim, 4 benchmark scenarios → solve potency (§8)
        │    └─ too strong even at the lowest potency, or blows the engine budget → repair once, else reject
        │
        6. Save (status = ready) → push to waiting clients over SSE
        │
        7. Everything failed → save the offline-combiner spec (§9) as status = provisional;
             the pre-generation worker retries it later
```

**Why two stages:** small local models are much better at *either* inventing *or* translating
into a strict format than at doing both at once. Stage A gets high temperature and loose
structure. Stage B gets low temperature and strict structure. It costs about 2× tokens, but it
should noticeably raise both creativity and the rate of valid specs. The eval harness (§12)
will measure that.

**Ollama details**
- `POST /api/chat` with `format: <JSON Schema>` (structured outputs) guarantees parseable JSON
  that matches the schema's shape. We still do semantic checks, since the schema can't express
  things like "references resolve".
- `keep_alive: "30m"` keeps the model loaded. `num_ctx: 16384` (the prompt is about 5–7k
  tokens). `OLLAMA_NUM_PARALLEL` lets player jobs and pre-generation run side by side.
- The model is configurable. Start with a ~8–14B instruct model that handles JSON well (Qwen,
  Llama or Gemma families) and pick with the eval harness, not by feel.
- An `LLMProvider` interface wraps the calls, so any OpenAI-compatible endpoint can be swapped
  in later with no pipeline changes.

## 7. Making every fusion unique (anti-blandness toolkit)

1. **Invented nouns.** Custom statuses, projectiles and zones mean the model creates new things
   instead of just picking from a menu. The lint requires at least one invented template, or at
   least one "uncommon" block (tagged as such in the registry).
2. **Twist seed.** A deterministic `hash(key)` picks one of about 150 hand-written mechanic
   seeds, and the prompt asks for it to be the **centerpiece**. Examples: *debt (power now,
   payback later) · resonance · inversion · pilgrimage · harvest · clockwork · memory ·
   metamorphosis · tides · sacrifice · orbit · contagion · symbiosis · mirrors · gravity wells ·
   rhythm · hunger · lanterns · erosion · crystallization · migration*. Because it's
   deterministic, retries of the same key keep the same theme.
3. **Fusion lint** rejects a spec when:
   - every rule is just a passive stat change,
   - `on_hit` is the only trigger used,
   - it's a near copy of one component's base spec,
   - it uses fewer than 4 distinct blocks,
   - the tags of any component power aren't represented anywhere in it.
4. **Novelty check.** Each spec gets a structural signature: the multiset of `trigger→action`
   edges, invented template kinds, and the motion and shape types it uses. That signature is
   compared by Jaccard similarity against fusions that share a tower and at least one power.
   Anything above 0.8 is rejected with feedback ("too similar to *Frostbite Relay*: both are
   on_hit → chill → chain"). Names must be unique. Optional: embedding similarity on `concept`
   through Ollama's embeddings endpoint.
5. **Rotating, contrasting examples.** Few-shot examples rotate and are chosen to be *unlike*
   the components, so the model doesn't copy the nearest one.
6. **Chassis cards.** Every tower describes its verb ("a beam that ramps up on one target"), so
   the same trio comes out differently per tower (see §5).

## 8. Balance by simulation: the LLM decides the shape, the server decides the numbers

- Damage is always written relative to tower stats (`{dmg: x}`). **Potency P** multiplies every
  damage coefficient. Crowd-control durations scale with √P, capped by hard limits. Slow
  percentages don't scale (they have fixed caps). Structural counts (how many projectiles, how many chains) are never scaled.
- The **headless sim** is the same `packages/sim` code the client runs. It runs **4 benchmark
  scenarios** of 60 s each on a fixed seed:
  **Boss** (one huge HP bar) · **Swarm** (40 weak) · **Armored column** · **Mixed** (flyers,
  shields, healers).
- Metrics: effective damage (HP actually removed), control-seconds (slow, stop and push-back,
  weighted), leaks, gold generated.
- **Score** is a blend: 0.6 × mean + 0.4 × best scenario. Specialists count as good, but only
  if they're great at their specialty.
- **Target bands** (placeholders to tune; 1.0 = the same tower at the same tier with no powers):
  single ≈ 1.25 (hand-tuned) · pair ≈ **1.55 ± 0.10** · triple ≈ **1.90 ± 0.12**
- **Solving potency:** binary search P in [0.2, 3.0], about 8 steps. If P is at 0.2 and the
  score is still over the band, the design is broken (for example, a perma-freeze loop), so
  send it to repair. If P is at 3.0 and the score is still under, accept it as "niche"; the
  engine caps keep it safe.
- **Cost:** a few seconds of CPU in a `worker_thread`. That's well under the LLM's own time.
- The same harness balances **our own content** (singles, towers, waves). Balance numbers come
  from one tool.

## 9. Offline combiner (fallback, and what the base game uses)

A deterministic merger with no server:
1. Put together the component powers' base rules, each scaled to 0.6 potency.
2. Add one **twist template** picked by `hash(key)` from about 40 hand-written ones (e.g.
   "Resonance: every 6th hit re-applies all your statuses", "Afterimage: kills leave a copy of
   the attack that fires once").
3. Give it a generated name from syllable tables ("Ember-Storm Arc").
4. Run the potency solve locally (it's the same sim).

This makes the game **complete with no server**. Unforged fusions are decent. The LLM fusions
are what make them special.

## 10. Safety and engine limits

- **Specs are data** run through whitelisted blocks. There's no `eval` and no code execution,
  so they're safe to share with every player.
- **Limits are enforced at runtime too**, not just when validating, so a tampered DB row can't
  freeze a client:
  - rules ≤ 6 · actions per rule ≤ 5 · statuses, projectiles and zones ≤ 2 each · vars ≤ 3
  - spawn depth ≤ 3 (a rule-spawned entity whose hit spawns entities, and so on)
  - ≤ 60 live entities spawned per tower · ≤ 64 rule events per tower per tick (extras are dropped)
  - min 0.1 s cooldown on spawn actions fired from `on_hit` · chain hops ≤ 8 · radius ≤ 4 tiles ·
    zone duration ≤ 10 s
  - gold per tower per wave capped · at most 1 life restored per wave · boss tenacity ·
    freeze immunity window
- **Text:** length limits, always rendered as text (never `innerHTML`), a blocklist filter on
  name and flavor, and an admin rename tool.

## 11. Storage and API

### SQLite schema (sketch)
```sql
CREATE TABLE fusions (
  key              TEXT PRIMARY KEY,        -- v1:arc:echo+frost+storm
  tower_id         TEXT NOT NULL,
  power_ids        TEXT NOT NULL,           -- JSON array, sorted
  status           TEXT NOT NULL,           -- ready | provisional | failed
  name             TEXT NOT NULL UNIQUE,
  concept          TEXT NOT NULL,
  flavor           TEXT NOT NULL,
  spec_json        TEXT NOT NULL,           -- validated effect-language spec
  potency          REAL NOT NULL,
  sim_report_json  TEXT,                    -- per-scenario metrics
  signature        TEXT NOT NULL,           -- structural signature for novelty checks
  dsl_version      INTEGER NOT NULL,
  content_version  INTEGER NOT NULL,        -- version of base towers/powers used
  prompt_version   INTEGER NOT NULL,
  model            TEXT NOT NULL,
  attempts         INTEGER NOT NULL,
  discovered_by    TEXT,                    -- player id (display name looked up)
  discovered_at    INTEGER,
  times_forged     INTEGER NOT NULL DEFAULT 0,
  upvotes          INTEGER NOT NULL DEFAULT 0,
  downvotes        INTEGER NOT NULL DEFAULT 0
);
CREATE INDEX fusions_by_tower ON fusions(tower_id);

CREATE TABLE generation_log (              -- every LLM call, used to tune prompts
  id INTEGER PRIMARY KEY, key TEXT, stage TEXT, prompt_version INTEGER, model TEXT,
  raw_output TEXT, errors TEXT, ms INTEGER, created_at INTEGER
);

CREATE TABLE players (id TEXT PRIMARY KEY, display_name TEXT, created_at INTEGER);
```

### HTTP API
| Method | Path | Purpose |
| --- | --- | --- |
| GET | `/api/fusions/:key` | 200 with the fusion, or 404 |
| POST | `/api/forge` `{tower, powers, playerId}` | 200 (cached) or 202 `{jobId, queuePosition}` |
| GET | `/api/jobs/:id/events` | SSE: `queued(pos) → concept → compile → validate → balance → done(fusion)` or `provisional(fusion)` |
| GET | `/api/codex?tower=&power=&sort=recent\|popular&cursor=` | Browse discovered fusions |
| POST | `/api/fusions/:key/vote` | 👍 / 👎 |
| GET | `/api/stats` | Discovered / total, recent world-firsts |

- **Identity:** anonymous. A random player id plus a display name kept in localStorage. No
  accounts at first.
- **Rate limits:** at most 3 queued forges per player, plus per-IP limits.
- **Client cache:** fusions never change per key and version, so they're cached in IndexedDB.
  Fusions you've already seen work offline.

## 12. Pre-generation and the eval harness

- **Pre-generation worker:** at idle priority it generates (1) every tower×pair before launch,
  (2) triples weighted by how popular their powers are, and (3) retries of `provisional` rows.
- **Eval harness (`tools/eval`):** a fixed set of 60 combos runs through the whole pipeline for
  a given model and prompt version. It reports:
  - first-try valid %, repair success %, lint pass %
  - novelty (mean pairwise signature distance)
  - potency distribution (lots of results stuck at the clamps means badly shaped designs)
  - p50/p95 latency

  A small **review page** shows a grid of results (name, concept, generated tooltip) with
  👍/👎, so we can compare prompt versions quickly.

## 13. Versioning

- `dsl_version` on every spec. The interpreter keeps migrations, so old specs keep working
  forever.
- `content_version`: when a base tower or power changes, existing fusions **keep their shape**
  (it's canonical and was discovered by someone), but a batch job re-solves their potency.
- `prompt_version` and `model` are stored on every row and in the log, so quality can be
  analyzed.
- An admin-only **"reforge"** exists for truly broken or offensive rows. It keeps the discoverer
  credit.
